## 0. 一页速览

**一句话设计**：Note 是一篇 Markdown，Block 是里面的陈述句，Card 是对 Block 的提问。
**提问写在笔记里，复习进度写在笔记外。**

| 层 | 是什么 | 落在哪 |
| --- | --- | --- |
| Note | 一个主题 / 一本书 / 一次复盘 | 一个 `.md` 文件（沿用现有仓库模型） |
| Block | 一句自洽的原子陈述 | 笔记里的一个列表项（或带 `^id` 的段落） |
| Card | 对 Block 的一个角度的提问 | Block 下缩进的 `- ?` 子项，或 Block 里的 `{{挖空}}` |
| 复习状态 | 到期时间、间隔、熟练度 | 仓库的 `.rnote/` 目录，**不写进笔记** |

三条设计原则：

1. **笔记是唯一事实来源。** 内容 100% 是纯 Markdown，用 Obsidian / VS Code 打开都正常；RNote 只是给它加了一层"可提问"的解读。
2. **写的时候零负担，要复习时才落标记。** 随手写列表就是 Block；只有当你要对它提问时，工具才补上 `^id`。
3. **进度与内容分离。** 复习一次就改一次笔记文件，会导致文件时间戳乱跳、和编辑器抢写、Git 全是噪音。所以进度单独存。

## 1. 产品设计补全（你文档里空着的第 4–8 章）

### 4 用户工作流：从"读过"到"会用"

RNote 的一天，只有四个动作：

```
  ┌─ 1. 读 ────────────┐   ┌─ 2. 提炼 ──────────┐
  │ 读书/上课/做项目    │   │ 把理解写成 Block    │
  │ 笔记照常记          │ → │ （陈述句，一句一事） │
  └────────────────────┘   └─────────┬──────────┘
                                     │
  ┌─ 4. 复习 ──────────┐   ┌─────────▼──────────┐
  │ 到期卡片自动出现    │   │ 3. 提问             │
  │ 回忆 → 评分 → 排期  │ ← │ 回忆 / 应用 / 辨析   │
  └────────────────────┘   └────────────────────┘
```

**关键点：第 2 步和第 3 步是同一个动作的两半。** 传统工具里"记笔记"和"做卡片"是两个软件、两份工作；RNote 里你写完一句 Block，顺手在它下面写一行 `- ?`，卡片就诞生了——提问的成本被压到几乎为零，这才是三层模型真正的产品价值。

**为什么强调"必须自己写 Block"**：现成的闪卡牌组是别人的理解，抄一遍只过了手，没过脑。RNote 刻意不提供"一键导入别人的牌组"，因为**提炼 Block 本身就是学习发生的地方**。

### 5 产品优势：RNote 不是又一个 Anki，也不是又一个 Notion

| 对比 | 它们的做法 | RNote 的做法 |
| --- | --- | --- |
| Anki / 背单词 App | 卡片是独立实体，脱离上下文，只有"背" | 卡片永远挂在 Block 上，复习时能看到所属 Note 与小节——**记忆带着上下文回来** |
| Notion / Obsidian | 只有"记录"，理解到记忆之间断了一环 | 记录与提问在同一个文件里，不用导出、不用同步 |
| RemNote | 思路接近，但数据在它自己的云里 | **纯 Markdown 存在你自己的文件夹**，随时能走 |
| 大纲笔记 | 结构靠人维护，容易越写越乱 | 三层是强约束：Note 定主题、Block 保原子、Card 逼你想 |

一句话：**别的工具要么只帮你记住，要么只帮你记下；RNote 帮你先把话说明白，再让它长在记忆里。**

### 6 最佳实践指南

**Block 的三条铁律**（来自你的文档，这里给出可操作的判据）：

| 铁律 | 反例 | 正例 | 自检问题 |
| --- | --- | --- | --- |
| 原子性 | "卡尼曼讲了认知偏差、双系统、前景理论" | "锚定效应是指判断过度依赖最先获得的信息" | 这句话能拆成两句吗？能就拆 |
| 自洽性 | "如上所述，它有三个特点" | 把"它"换成具体的名词 | 单独摘出来能看懂吗？ |
| 可提问性 | "本章很有意思" | 一个能被追问"是什么/为什么/怎么用/和什么不同"的陈述 | 我能对它提出至少一个问题吗？ |

**提问的四个角度**（你说的三种，我补一种）：

| 角度 | 句式模板 | 例子 |
| --- | --- | --- |
| 回忆 | X 是什么 / X 有哪些特点 | 锚定效应的定义是什么？ |
| 应用 | 在……场景下怎么用 X | 在产品定价中如何利用锚定效应？ |
| 辨析 | X 和 Y 有什么区别 / X 不适用于什么情况 | 锚定效应和可得性启发有何区别？ |
| 追问 | 为什么 X 成立 / X 的前提是什么 | 为什么锚定效应在无意识下也会发生？ |

**建议节奏**：读一章 → 写完 5–10 个 Block → 每个 Block 至少一张"回忆"卡、重点 Block 补一张"应用"或"辨析"卡 → 当天不复习，第二天开始。**不要一边读一边做卡**，提炼需要读完一节之后的整体视角。

**反模式**：
- ❌ 把整段原文复制成 Block（那是摘抄，不是理解）
- ❌ 一个 Block 挂十几张卡（说明 Block 不够原子）
- ❌ 只做回忆卡（会背不会用，正是你文档开头批评的"死记硬背"）
- ❌ 追求卡片数量（复习量爆炸 → 放弃 → 前功尽弃）

### 7 未来展望

- **智能提炼助手**：选中一段原文，让模型给出 2–3 个候选 Block（陈述句形式），你只做取舍——**永远由你按下确认键**。
- **卡片草稿生成**：给一个 Block，按四个角度生成问题草稿（答案始终是 Block 原文，模型不写答案，避免它替你理解）。
- **Anki 导出**：`.apkg` 导出，格式已经天然对应（正面=问题，背面=答案+上下文）。
- **多端同步**：笔记是普通文件，交给 Syncthing / iCloud / Git 即可；`.rnote/` 状态文件做成可合并的 JSON。
- **协作复习**：同一个仓库里，Block 可以标注"谁提出的问题"。

### 8 开始使用（5 分钟）

1. 打开 RNote，选一个文件夹作为仓库
2. 新建笔记，用列表写下三句你今天真正理解的话
3. 在每句话下面按 `Tab` 缩进，输入 `- ? 你想问的问题`
4. 切到「复习」页，你会看到 3 张卡
5. 合上屏幕前，把明天的到期卡片过一遍——结束了

## 2. 数据格式（核心设计）

### 2.1 三层到 Markdown 的映射

```markdown
# 思考，快与慢                          ← Note：一个文件 = 一个主题

## 系统 1 与系统 2                       ← 小节：只提供上下文，不是知识单元

- 系统 1 是快速、自动、几乎不费力气的直觉系统。 ^sys1
                                        ↑ Block：一句陈述句 + 稳定 id
    - ? 系统 1 的特点是什么？            ← Card：对 Block 的提问（回忆）
    - ? 为什么说系统 1 很难被主动关闭？ | 应用
                                        ↑ 角度标签
- 锚定效应是指人们在做判断时过度依赖{{最先获得的信息}}。 ^anchor
                                     ↑ 挖空：自动生成填空卡
    - ? 在产品定价中如何利用锚定效应？ :: 先抛出高参考价，让售价显得便宜。 | 应用
                                     ↑ 显式答案（不写就用 Block 原文当答案）
```

### 2.2 Block 的三种写法

| 写法 | 什么时候用 | 是否自动获得 id |
| --- | --- | --- |
| `- 陈述句` | 常规：用列表写笔记，天然是树 | 暂时没有，需要卡片时工具补上 |
| `- 陈述句 ^id` | 已挂卡片 / 需要在别处引用 | 有（Obsidian 的块引用同款语法） |
| `　　陈述句 ^id`（段落 + 行尾 id） | 不想用列表、想写成段落 | 有 |

**为什么 Block 默认是"列表项"**：你的文档说 Block 应该是"一个完整的陈述句"，而列表本来就是"一条一条的陈述"；同时列表的缩进天然表达了 Block 之间的父子/并列关系，正好对应你说的"枝干之间可以交错、呼应，但各自独立"。**笔记的 Markdown 缩进结构 = 知识树的形状**，不需要额外的树编辑器。

### 2.3 Card 的两种形态

**问答卡**：`- ? 问题`，可选 `:: 显式答案`，可选 `| 角度`

```markdown
- ? 系统 1 的特点是什么？                    → 答案 = Block 原文
- ? 定价中怎么用锚定效应？ :: 先抛高参考价。   → 答案 = 冒号后内容
- ? 系统和直觉有何区别？ | 辨析               → 带角度标签
```

**填空卡**：Block 里写 `{{要挖掉的部分}}`，一处挖空 = 一张卡；多个挖空时，评测其中一处、其余自动还原成明文（Anki 的标准做法）。

```markdown
- 锚定效应是指人们在做判断时过度依赖{{最先获得的信息}}。
  → 卡片正面：锚定效应是指人们在做判断时过度依赖______。
  → 卡片背面：最先获得的信息
```

### 2.4 复习状态放在哪：三个方案的取舍

| 方案 | 做法 | 优点 | 致命问题 |
| --- | --- | --- | --- |
| A. 写进笔记 | 文件末尾加 `<!-- rnote:state -->` | 单文件自包含 | **每复习一次就重写笔记**：编辑器和复习抢写、时间戳乱跳、Git 全是噪音、冲突检测天天误报 |
| B. 每篇一个伴生文件 | `note.md` + `note.rnote.json` | 不污染正文 | 文件数翻倍，移动/重命名笔记要跟着搬，容易孤儿 |
| **C. 仓库级状态库（采用）** | `.rnote/schedule.json` | 正文零改动、查询快、能全局算"今天到期" | 状态不跟着笔记走（复制笔记到别处会丢进度） |

**选 C**，理由：

- 复习是**高频写**（一天几百次评分），笔记内容是**低频写**（一天几十次编辑）。把一个高频写的东西塞进低频写的文件里，是最典型的存储设计错误。
- 全局视图（今日到期、热力图、连续天数）本来就需要跨笔记聚合，放一个文件里查询是 O(1) 而不是 O(笔记数)。
- 代价（进度不随笔记走）可以接受：进度是"我对这篇笔记的熟练度"，它本来就该跟着**仓库里的这个人**走，而不是跟着文本走。真要迁移，提供导出/导入即可。

```
仓库/
  .rnote/
    schedule.json     # 每张卡的排期
    review-log.jsonl  # 每次评分的历史（算热力图/留存率）
    config.json       # 每日上限、算法版本等
  思考快与慢.md
  ...
```

```jsonc
// schedule.json 片段
{
  "version": 1,
  "cards": {
    "思考快与慢.md::sys1#0": {
      "due": "2026-10-08",      // 到期日
      "interval": 3,            // 当前间隔（天）
      "ease": 2.5,              // 难度系数
      "reps": 4,                // 连续答对次数
      "lapses": 1,              // 遗忘次数
      "fingerprint": "bstr4t",  // 问题指纹，编辑后认回用
      "last": "2026-10-05"
    }
  }
}
```

### 2.5 卡片身份与编辑容错

卡片主键 = **`笔记路径 :: blockId # 序号`**。

| 你做了什么 | 会发生什么 |
| --- | --- |
| 改 Block 的文字 | 主键不变（靠 `^id`），**复习进度完整保留** ✅ |
| 改问题文字 | 序号不变则进度保留；变了口气也没关系 |
| 在中间插入一张新卡 | 后面卡片的序号全漂一位 ⚠️ |
| 删掉 Block | 状态成为孤儿，下次清理时归档（不立刻删，万一你只是改错了） |

序号漂移靠 **指纹（fingerprint）** 兜底：每张卡记录"问题文本去掉空白与标点后"的哈希。同步时先按主键匹配，对不上的再按指纹匹配——**只要你没改问题的实质内容，进度就认得回来**。这一点已经写进解析器并验证过（见 §2.7 的最后两条断言）。

### 2.6 格式带来的额外好处：Obsidian 能直接用

`^id` 不是我们发明的，它是 **Obsidian 原生的块引用语法**（`[[笔记#^sys1]]` 可以精确引用到一个 Block）。所以：

- 用 Obsidian 打开这个仓库：`^id` 被识别为块引用，`- ? ...` 就是一条普通的嵌套列表，**不会报错、不会破坏文件**；
- 用 RNote 打开：同样的文件多出一层"卡片"结构；
- 用 Git 管理：纯文本 diff，语义清晰。

**这意味着 RNote 的数据没有锁定风险**——即使这个应用哪天不做了，你的笔记一行都不会丢。

### 2.7 已验证的解析行为

样例文件 [`docs/rnote-sample.md`](rnote-sample.md)，验证脚本 [`scripts/rnote-check.ts`](../scripts/rnote-check.ts)：

```bash
node scripts/rnote-check.ts    # 24 项断言全部通过
```

实测解析输出（节选）：

```
标题: 思考，快与慢
Block 数: 4，卡片数: 7

● [sys1] 系统 1 是快速、自动、几乎不费力气的直觉系统。
  小节: 系统 1 与系统 2
  └─ (问答) 系统 1 的特点是什么？          答: 系统 1 是快速、自动、……   key=sys1#0
  └─ (问答 #应用) 为什么说系统 1 很难被主动关闭？
  ● [sys2b] 系统 2 并不会主动接管判断……      ← 嵌套 Block，depth=1，parent=sys2
● [anchor] 锚定效应是指人们在做判断时过度依赖{{最先获得的信息}}。
  └─ (问答 #应用) 在产品定价中如何利用锚定效应？  答: 先抛出一个高参考价……
  └─ (填空) 锚定效应是指人们在做判断时过度依赖______。  答: 最先获得的信息
```

开发过程中这轮验证抓出了 4 个真实缺陷，都已修掉——**这就是先写解析器再定文档的价值**：

1. `- [ ] 待办` 被误判成 Block（任务不是知识单元）
2. `:: 答案 | 标签` 里，标签被并进了答案（必须先摘标签再切答案）
3. Block 的小节上下文把一级标题（笔记标题）也算进去了，导致复习时显示"思考，快与慢 › 系统 1 与系统 2"这种重复信息
4. 默认答案保留了 `{{ }}` 标记（展示用的 `plain` 字段应展开挖空）

## 3. 界面与交互

### 3.1 编辑态：让 Block 和 Card 看得见

编辑区基本沿用现有 CodeMirror，只加三处装饰：

```
┌─ 思考快与慢.md ─────────────────────────────────────────────┐
│  1   # 思考，快与慢                                          │
│  2                                                          │
│  3   ## 系统 1 与系统 2                                      │
│  4                                                          │
│  5 ● 系统 1 是快速、自动、几乎不费力气的直觉系统。      ⟨2⟩   │
│  6     ▸ 系统 1 的特点是什么？                                │
│  7     ▸ 为什么说系统 1 很难被主动关闭？  应用                │
│  8 ● 系统 2 是缓慢、需要注意力、消耗心力的理性系统。    ⟨1⟩   │
└─────────────────────────────────────────────────────────────┘
    ↑ 行首圆点 = 这是 Block      ↑ 卡片行特殊着色、显示角度标签
    ↑ 右侧 ⟨n⟩ = 已挂 n 张卡     ↑ `^id` 在非光标行自动隐藏
```

- 行首圆点：一眼看出哪些句子已经"成块"
- `⟨2⟩`：这张 Block 上有几张卡，点一下展开卡片面板
- `^id` 在非光标行淡化/隐藏（复用现有实时预览插件，同一套 Decoration 机制）
- 卡片行用主题色左侧竖线标记，和正文拉开层次

### 3.2 提炼：把普通笔记变成 Block

现有笔记不用重写，选中一段按 `Ctrl+Shift+B`：

| 选中的内容 | 结果 |
| --- | --- |
| 一行普通段落 | 原地转成列表项并分配 `^id` |
| 多行段落 | 每段成一个 Block，连续分配 id |
| 已经有 `^id` | 什么都不做（幂等） |

### 3.3 造卡：一条命令，三个角度

光标停在 Block 上按 `Ctrl+Shift+C`，从 Block 上"长"出卡片：

```
┌─ 为这个 Block 添加卡片 ────────────────────────────────┐
│ 系统 1 是快速、自动、几乎不费力气的直觉系统。            │
│                                                        │
│ 角度：  [回忆] 应用  辨析  追问        ← 单选，决定模板  │
│                                                        │
│ 问题：  系统 1 的特点是什么？                          │
│         ✨ 生成草稿  ← 可选，模型只写问题、不写答案      │
│                                                        │
│ 答案：  ○ 使用 Block 原文（推荐）  ○ 自定义             │
│                                                        │
│                              [取消]  [添加]             │
└────────────────────────────────────────────────────────┘
```

**答案默认永远是 Block 原文**——这是产品理念的技术体现：卡片只是"探询的角度"，知识本体始终是那句 Block。

```
│  ↳ 来源：思考，快与慢 › 系统 1 与系统 2      [打开笔记]   │  ← 上下文永远可见
```

要点：

- **上下文常驻**：卡片顶部/底部始终显示"来自哪篇笔记的哪一节"，这就是和 Anki 最大的体验差别；点一下直接跳回原文对应行
- 键盘全流程：`空格` 翻面、`1–4` 评分、`Ctrl+Z` 撤销上一次评分（手滑救星）
- 不做"再来一次/稍后提醒"这类按钮，只保留四档评分，减少决策负担

### 3.5 知识树：你要的那棵会生长的树

侧边栏第三个标签页，把当前笔记渲染成树（对应你文档第 3 章的隐喻）：

```
🌳 思考，快与慢
├─ 系统 1 是快速、自动、几乎不费力气的直觉系统。      🍃🍃
│  ├─ 系统 1 的特点是什么？                    （复习过 3 次）
│  └─ 为什么说系统 1 很难被主动关闭？
├─ 系统 2 是缓慢、需要注意力、消耗心力的理性系统。    🍃
│  └─ 系统 2 并不会主动接管判断……                 🍃
│     └─ 系统 2 什么时候才会介入？
└─ 锚定效应是指……依赖{{最先获得的信息}}。          🍃🍃🍃
```

- 🍃 数量 = 卡片数；颜色深浅 = 熟练度（生疏→熟练）
- 折叠/展开，点击跳转到原文
- 这棵树是**只读视图**，树的形状由 Markdown 缩进决定——不需要单独的编辑器，改笔记就是改树

## 4. 复习算法

### 4.1 四档评分

| 键 | 含义 | 判定标准 |
| --- | --- | --- |
| 1 重来 | 完全没想起来 | 看了答案才想起来 |
| 2 困难 | 想起来了，很吃力 | 犹豫、回忆不完整 |
| 3 记得 | 顺利想起来 | 正常 |
| 4 简单 | 秒答 | 太简单了，没必要这么频繁 |

**不给"模糊"档**：评分档位越多，人越会纠结，宁可四档、语义清晰。

### 4.2 v1：SM-2（先做对，再做好）

```
重来(1)：reps=0, interval=1 天, ease-0.2     ← 回到明天
困难(2)：interval = max(1, interval × 1.2), ease-0.15
记得(3)：interval = interval × ease, ease 不变
简单(4)：interval = interval × ease × 1.3, ease+0.15

ease 钳制在 [1.3, 2.8]；
首次：记得 → 1 天，简单 → 4 天；
interval 上限 365 天；
每天新卡上限 20（可配）。
```

30 行代码，行为可解释，够用到卡片上几千张。

### 4.3 v2：FSRS

上量之后换成 FSRS（Rust 有 `fsrs` crate，与现有 Tauri 后端天然契合）。相比 SM-2，它按"记忆稳定性 + 难度"两维建模，**在同等留存率下能减少 20–30% 的复习量**。接口不变（还是四档评分），只换调度内核，状态文件里加 `stability` / `difficulty` 字段并标注 `algorithm: "fsrs"` 以便平滑迁移。

### 4.4 到期查询

```
今日到期 = 所有卡片中 due <= 今天 的集合，按 due 升序、再按熟练度升序
新卡 = 从未复习过的卡片，每天最多取 N 张
```

数据量级估算：1 万张卡片，`schedule.json` 约 1–2 MB，全量加载进内存即可毫秒级查询；超过 5 万张再考虑换 SQLite（接口不变）。

## 5. 系统架构与落地

### 5.1 现有 Highland Note 能复用什么

| 现有能力 | RNote 怎么用 |
| --- | --- |
| 仓库模型 / 文件树 / 搜索 | 直接用，RNote 不需要新的存储层 |
| CodeMirror 编辑器 + 实时预览插件 | 加两个 Decoration：淡化 `^id`、标记卡片行 |
| markdown-it 渲染管线 | 加两个 rule：隐藏 `^id`、把 `{{}}` 渲染成高亮 |
| Tauri 命令层 | 加 5 个命令（下面 §5.2） |
| 深色/浅色主题、原子右键菜单 | 复习界面复用同一套变量与组件 |

**结论：RNote 不是重写，是在现有应用上加一层"卡片层"。** 这也是当初把笔记做成纯 Markdown 的回报。

### 5.2 新增模块清单

```
src/lib/
  rnote.ts        ✅ 已完成并验证：Note/Block/Card 解析、指纹
  review.ts       调度算法（SM-2 → FSRS）
  schedule.ts     排期状态的读写与合并（含指纹兜底匹配）
src/components/
  CardPanel.vue       右侧卡片面板（看/加/删某 Block 的卡）
  CardComposer.vue    造卡对话框（角度模板 + 草稿）
  ReviewView.vue      全屏复习
  KnowledgeTree.vue   知识树视图
  ReviewDashboard.vue 统计与热力图
src-tauri/src/
  review.rs       due 查询、评分落盘、孤儿状态清理
  settings.rs     扩展：每日上限、新卡上限、算法版本
```

### 5.3 数据流

```
编辑笔记 ──保存──► Markdown 文件（唯一事实来源）
                      │
                      │ 解析（前端每次保存后增量解析，或用 Rust 侧全仓库解析）
                      ▼
              Block / Card 结构（内存）
                      │
        ┌─────────────┴──────────────┐
        │                            │
   卡片面板 / 知识树            复习视图
        │                            │
        │  提问写回 Markdown          │ 评分
        ▼                            ▼
   笔记文件                     .rnote/schedule.json
```

关键约束：**复习只写 `.rnote/`，提问/编辑才写笔记。** 两条写路径彻底分开，永不相撞。

### 5.4 Tauri 命令（新增）

| 命令 | 作用 |
| --- | --- |
| `scan_cards(vault)` | 全仓库扫描，返回所有 Block/Card（带笔记路径与行号） |
| `due_cards(vault, date)` | 今日到期 + 新卡配额 |
| `grade_card(vault, key, rating, elapsed)` | 评分落盘，返回下次到期 |
| `card_stats(vault)` | 热力图、留存率、连续天数 |
| `write_block_id(vault, path, line, id)` | 给 Block 补写 `^id`（提炼命令用） |

`scan_cards` 用 Rust 的 `walkdir` + 正则做，和现有 `search_notes` 同一套路子；解析规则要和前端 `rnote.ts` 保持一份"规范"，建议以 `docs/rnote-sample.md` 作为跨语言的一致性测试样本（两端都跑同一份断言）。

## 6. 路线图

### 阶段一：闭环能跑（最小可用）

1. `rnote.ts` 解析 ✅ **已完成**
2. 编辑器装饰：Block 圆点、`^id` 隐藏、卡片行着色
3. `Ctrl+Shift+C` 造卡（先不做 AI 草稿）+ 右侧卡片面板
4. 复习视图 + SM-2 + `.rnote/schedule.json`
5. 侧边栏「复习」入口 + 今日到期徽标

**验收标准**：能完整走一遍"写 Block → 提问 → 第二天复习 → 评分 → 一周后重逢"。

### 阶段二：好用

6. 知识树视图（你要的那棵树）
7. 填空卡 `{{}}` 的编辑体验（选中文字一键挖空）
8. 统计仪表盘（热力图、留存率、连续天数）
9. `Ctrl+Shift+B` 从旧笔记批量提炼 Block
10. 复习中的 `Ctrl+Z` 撤销评分、`直接跳回原文`

### 阶段三：智能与生态

11. FSRS 调度内核
12. AI 造卡草稿（**只生成问题、不生成答案**）
13. Anki `.apkg` 导出
14. 笔记内嵌复习小组件（在正文里直接看到某张卡的状态）

### 风险与取舍

| 风险 | 应对 |
| --- | --- |
| 用户不写 Block，直接拿整段当 Block | 造卡时检测"这句话超过 80 字/含多个句号"→ 提示"要不要拆成两句？" |
| 复习量爆炸导致放弃 | 每日上限 + 新卡配额 + 仪表盘显示"积压"预警；宁可少给，不可多给 |
| Block 的 `^id` 让正文变脏 | 编辑器默认隐藏、预览不渲染；只在你需要引用时看见 |
| 卡片序号漂移丢进度 | 指纹兜底（已实现并验证） |
| 和 Obsidian 双开编辑冲突 | 沿用现有 mtime 冲突检测；`.rnote/` 状态与正文分离，天然不冲突 |
| 用户只想记笔记、不想复习 | 三层是**可选**的：不写 `?` 就完全是普通 Markdown 笔记，零打扰 |

### 最后的取舍说明

**为什么不做成独立应用**：RNote 的价值在"记录"和"记忆"之间，把它拆成两个 App 就又把那道断层还回来了。它应该是现有笔记应用里的一个**模式**——写作时是笔记，想起来时是卡片。

至于产品名：现有工程叫 `highland_note`，产品叫 RNote。建议**界面统一用 RNote**（用户认知），仓库/包名保持 `highland_note`（改动成本为零），等真要发布时再统一。
